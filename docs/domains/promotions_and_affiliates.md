# 推广与返利

本文描述邀请关系、订单返利、冻结和解冻、余额转入和注册优惠码的不变量。支付渠道的回调字段、营销页面的文案和管理员操作教程在其他资料里。

推广规则、值类型和优惠码用例在 `promotion`，持久化在 `promotion/postgres`，管理员和用户的 HTTP 在 `promotion/httpapi`。app 构造一个实例，并绑定 identity、billing 以及设置和缓存的接口。identity、billing 和 payment 通过各自需要的小接口调用推广功能。

## 邀请关系

每个用户有一份推广档案和一个唯一的邀请码。邀请码去掉首尾空白并转成大写，只允许大写字母、数字、下划线和短横线，长度 4 到 32。管理员可以设置自定义邀请码，也可以恢复成系统生成的邀请码。

每个用户只能绑定一次邀请人，也不能邀请自己。推广总开关关闭时，注册阶段直接忽略邀请码，注册照常进行；开启后，格式错误、邀请码不存在或自己邀请自己，都返回明确的业务错误。用户已经有邀请人时，幂等地保留已有的关系；两个请求同时首次绑定时，只有一个生效，另一个返回已绑定错误。绑定关系按用户 ID 保存，邀请码之后改名，已有的邀请关系保持不变。

## 返利生命周期

支付订单完成后，以被邀请人实际获得的推理积分为基数计算返利。邀请人的专属比例优先于全局比例，结果按统一的精度舍入。返利还受邀请关系、总开关、邀请后的有效天数，以及每个被邀请人的累计上限约束。

计提返利时，先在 PostgreSQL 事务里锁住邀请人的推广档案，再读取这个被邀请人已经累计的返利，算出剩余额度；计算和写入在同一个事务里完成，有外层的支付事务时复用它的连接。所以两笔并发的计提不会各自按同一个旧的累计值把上限占满。

返利记录关联邀请人、被邀请人、金额、冻结时长和可选的来源订单。冻结时长为正时，先增加 frozen quota；否则直接增加 available quota。历史累计值同时更新，它是统计数据，转账使用的是 available quota。

已经到期的冻结记录，在读取推广详情或执行相关资金操作时，解冻为可用返利。解冻是持久化的资金状态变化，需要写入数据库；只在响应 DTO 里相加是不够的。管理端的统计分别展示可用、冻结和历史累计。

## 转入余额

用户可以把当前全部可用返利一次性转入主余额。promotion 的 PostgreSQL 适配层在事务里锁定并更新推广档案，通过 billing 的参与能力增加用户的余额和累计充值，再写一条转账记录；没有可用返利时返回业务错误。成功后，让余额、认证和推广相关的缓存失效，网关立即使用新余额。

转入是平台内部的余额调整，外部支付渠道不参与。余额变化之后，照常遵守计费、退款和审计规则；已经转入的余额无法通过删除推广记录撤回。

## 注册优惠码

Promo Code 在用户注册成功后赠送余额，字段包括 code、赠送金额、active 或 disabled 状态、过期时间、最大使用次数和已使用次数。`max_uses=0` 表示总次数不限；每个用户对同一个 code 最多使用一次。

使用优惠码时，在同一个数据库事务里给 code 加行锁，重新检查状态、过期时间和总次数，确认这个用户还没用过，再通过 billing 的参与能力增加余额，写入使用记录，并增加已使用次数。正数的 Promo 赠送同时增加余额和累计充值；普通的只加余额的入口不用于这个操作。事务提交后，再让余额和认证缓存失效。事务外的预校验只用于改善用户体验，最终以事务内的复核为准。

优惠码和邀请码可以在注册时一起使用，两者各管各的：优惠码直接给注册用户余额，邀请码建立以后订单返利的关系。Redeem Code、订阅和支付促销有各自的表和次数规则，不和 Promo Code 共用。

## 幂等与审计

订单返利用 `source_order_id` 关联来源。支付履约通过 `payment/postgres.OrderStore.ApplyOrderRebate` 在事务中先认领订单审计记录，再使用同一事务计提返利。`payment_audit_logs` 的 `(order_id, action)` 唯一索引和已应用、已跳过记录的检查共同处理回调重放。推广流水的 `source_order_id` 使用普通索引，直接调用 `promotion.AffiliateService.AccrueInviteRebateForOrder` 的调用方需要协调重复请求。

Promo Code 依靠唯一的使用记录和行锁，防止并发重复赠送。邀请码绑定、比例调整、解冻、转账和管理员改码，都保留操作记录或可审计的状态。

补偿时，先分别判断订单履约、返利记录和余额流水是否已经写入，只重试还没完成、并且有幂等保护的步骤。资金相关的缓存失效失败时发出告警，数据以数据库事务的结果为准。
